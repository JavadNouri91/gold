# Emergency database backup

Page: `/dashboard/settings/database-backup`. Download API: `GET /api/v1/admin/database-backup/download`.

The `database.backup.create` permission is granted to `store_manager` and `platform_admin` by migration `202611110003_database_backup_permission`. Apply migrations and reload the browser to refresh session permissions. Restart the API after adding the module; check `/api/docs-json` in development to confirm registration.

The default runner uses `pg_dump` on PATH, or `PG_DUMP_PATH` pointing to the executable. The production API Dockerfile installs PostgreSQL 16 client tools.

For a Windows host API with the local Docker database, set `DATABASE_BACKUP_DOCKER_CONTAINER=gold_postgres` in `apps/api/.env` and restart the API. Docker must be running and accessible to the API account. In this explicit mode, `pg_dump` executes inside that container and connects to the database from `DATABASE_URL`. Loopback hosts are translated to Docker Desktop's `host.docker.internal`; the configured port and database are preserved. Binary output is streamed into a private temporary file on the API host. Production deployments running the API inside Docker should leave this setting unset and use the installed native client.

Downloads use PostgreSQL custom archives (`.dump`), containing database schema and data. Uploaded files and server configuration are outside this database-only backup. Temporary files are removed after download or disconnection. There is no backup scheduler.

## Restore

The same page includes `POST /api/v1/admin/database-backup/restore` (multipart `file` and `confirmation=RESTORE`). Migration `202611110004_database_restore_permission` grants `database.backup.restore` only to `platform_admin`. Reload the browser after applying it. Files must be trusted custom PostgreSQL archives from the same application version, at most 256 MiB. The server checks the archive header and directory for the application's base tables; this is not a sandbox or a guarantee of version compatibility. PostgreSQL archives can execute SQL, so never restore files from untrusted sources.

The feature temporarily rejects new requests on this API instance and waits up to 30 seconds for existing requests to finish. It saves a safety dump before invoking `pg_restore --clean --if-exists --single-transaction --exit-on-error --no-owner --no-acl`. A failed SQL statement rolls back the restore transaction. Uploaded archives are removed afterward. The operation may take up to 15 minutes; configure the reverse proxy request/upload timeout and body limit accordingly. A lost HTTP response does not prove the database operation failed: inspect the server and database before retrying.

Safety dumps persist in `DATABASE_BACKUP_RECOVERY_DIR` (default `.data/emergency-recovery` relative to the API working directory, typically `apps/api/.data/emergency-recovery` locally). Docker Compose mounts a separate `emergency_recovery_data` volume at `/opt/gold/data/emergency-recovery`. The response reports the safety dump's filename. These files are sensitive and retained until the administrator removes them; keep storage space available. `PG_RESTORE_PATH` can override the executable on native installations.

This emergency tool supports one API instance. Before restoring a deployed environment, stop other API instances, background workers, integrations and direct database writers. The in-process maintenance middleware cannot pause those clients. Restoring an older schema may require the corresponding application release or migrations, and restores replace authentication/session records too. Sign in again with credentials present in the restored database. `--clean` drops objects present in the archive, not unrelated objects absent from it.

Validation: `node apps/api/scripts/verify-emergency-restore.cjs` creates a uniquely named disposable database in the local `gold_postgres` container, checks successful restore, safety dumps and transaction rollback on a deliberate dependency error, then drops only that disposable database. It never restores the live database.

## S3-compatible backup destination

The same dashboard page has a separate S3 destination with endpoint, region, existing bucket, dedicated prefix, access key, secret key, path-style addressing, and explicit HTTP opt-in for trusted local networks. Apply `202611110005_database_backup_storage_permission`; only `platform_admin` receives `database.backup.storage.manage` for changing the destination and testing it. Users with `database.backup.create` can upload newly generated backups, list stored dumps and download them. Restore a stored dump by downloading it and selecting it in the existing restore form.

Settings are encrypted with the shared settings encryption helper (`SETTINGS_ENCRYPTION_KEY`, with `JWT_ACCESS_SECRET` fallback) in `DATABASE_BACKUP_STORAGE_DIR/s3-settings.enc`. The local default is `.data/emergency-storage` relative to the API working directory. Docker Compose mounts `emergency_storage_data` at `/opt/gold/data/emergency-storage`. Preserve the encryption key and this directory separately from database backups. Credentials are never returned to the browser; blank credential fields preserve existing credentials. Changing the endpoint requires explicitly re-entering both keys. Configuration remains available after restoring the database because it is outside the database.

Use a private bucket and keys with `s3:PutObject` and `s3:GetObject` on the configured prefix, plus `s3:ListBucket` restricted to that prefix. The connectivity check verifies list/read access only; upload verifies writing and object metadata. The app does not create buckets, set public ACLs, delete stored backups, or change retention policies. Configure bucket lifecycle rules in the storage provider when needed. The endpoint must be the S3 API URL, not a console URL or a URL containing the bucket name.

Uploads stream to a unique object key, send a Content-MD5 integrity header, store SHA-256 metadata, and verify the remote size and SHA-256 metadata with HeadObject before reporting success. Downloads check the size and available SHA-256 metadata before sending the file. A single upload/download supports up to 5 GiB; the existing restore form remains limited to 256 MiB. List results are paginated (50 objects per request) within the configured prefix. Calls have finite timeouts. If a write succeeds but verification or the HTTP response is lost, refresh the object list before retrying.

The adapter uses the [official AWS S3 SDK](https://docs.aws.amazon.com/AWSJavaScriptSDK/v3/latest/Package/-aws-sdk-client-s3/Class/S3Client) with configurable endpoint and path-style addressing. Compatibility was verified with local MinIO. Run `node apps/api/scripts/verify-emergency-s3.cjs` to repeat the encrypted-settings, upload, list and verified-download checks with synthetic data in a temporary local MinIO bucket. Other providers must be verified using their own endpoint and keys.

To remove the feature: remove the `DatabaseBackupModule` import/registration from `app.module.ts`, its module directory (including its maintenance middleware), the frontend route/component, `backup-storage-panel.tsx` and `database-backup-api.ts`, the navigation entry and icon, and all three seed permission entries. Remove optional backup environment settings and the dedicated Compose recovery/storage-volume attachments; retain recovery files and storage settings until they are no longer needed. The PostgreSQL client package and `@aws-sdk/client-s3` dependency can also be removed if unused. Keep already-applied migration files in migration history; use a new migration to remove the permissions if desired. No business module imports this feature, and no business schema depends on it.
